# 瑪奇 Mobile 時裝時間軸重構設計規格

## 目標

把網站從「最新韓服項目列表」改成桌面優先、手機可用的完整韓服時裝歷史時間軸，並用可追溯的證據層級呈現台服對應狀態，避免把韓服最新內容誤讀成台服即將推出內容。

## 使用情境與設計方向

- 主要使用者是想查閱韓服時裝歷史、比較台服進度的瑪奇 Mobile 玩家。
- 桌面是主要閱讀場景；手機需支援單手瀏覽、搜尋、篩選與圖片切換。
- 首要任務是沿完整時間軸閱讀，不是只看最新項目。
- 視覺方向是編輯雜誌與清爽資料工具的混合：有年份／月份章節與留白，但資訊、狀態與證據要快速可讀。
- 所有台服推論都必須以「資料中已找到的對應」表述，不使用「下一期」「即將推出」等未被公告支持的語句。

## 現況問題

1. `js/app.js` 將月份與卡片以倒序顯示，最新韓服內容直接出現在入口位置。
2. 卡片只顯示單一名稱；未發行品項的韓文原名、已發行品項的台服官方名稱與雙語搜尋需求沒有結構化呈現。
3. `scripts/build-dataset.js` 的台服判斷以 CloudFront UUID 和人工 map 為主，名稱語意不是第一層證據；UUID 未命中會產生偽「未發行」。
4. `전설 패션 장비` 與 `토탈 패키지` 的分類語意需要固定為「傳說時裝」與「套組時裝」。
5. 樂器與染色劑選擇箱未以產品級資料完整呈現。
6. 圖片輪播主要依賴 hover 顯示箭頭，手機互動不完整；篩選只有單一分類與單一 checkbox。

## 設計

### 1. 頁面資訊架構

頁面由上至下分為：

1. **刊頭**：網站名稱、用途說明、韓服／台服官方來源連結。
2. **資料概覽**：收錄筆數、台服已確認筆數、待核對筆數，以及「台服資料截至」日期。這是資料狀態，不是排程預測。
3. **固定控制列**：搜尋、分類、台服狀態、排序、年份／月份跳轉與「跳到今天」按鈕。
4. **完整時間軸**：按年份與月份由舊到新分章；月份內卡片按韓服上線日正序排列。
5. **頁尾說明**：資料來源、判斷限制、版權與非官方聲明。

桌面可在時間軸旁提供輕量年份導覽；第一版不做額外資料頁或複雜路由，避免偏離靜態網站的簡單部署方式。

### 2. 時間軸

- 預設排序：韓服上線日期由舊到新。
- 提供「由新到舊」切換，但切換不改變資料本身。
- 顯示實際今天的標記與「跳到今天」操作；若目前日期落在資料範圍外，按鈕跳到最接近的資料章節。
- 頁首顯示台服最新已抓取公告日期，並提供「待台服對照」篩選。
- 不以韓服日期推測台服排程。若提供距離排序，名稱固定為「距離台服最新資料日期」，並加上說明「僅為時間距離，不代表台服發行順序」。

### 3. 卡片內容階層

每張卡片至少包含：

- 分類徽章。
- 台服狀態文字徽章，不只依靠顏色。
- 宣傳圖輪播、圖片數量、放大檢視；桌面箭頭與手機觸控滑動都可用。
- 主要名稱：有台服官方名稱且狀態為官方確認時顯示台服名稱；否則顯示韓服公告正式名稱。
- 次要名稱：永遠保留另一服名稱或韓文原名，方便搜尋與考據。
- 韓服上線日期。
- 若有確認對應，顯示台服上線日期、台服公告標題與公告連結。
- 「比對依據」摘要，點擊後可查看完整證據。

### 4. 台服對應證據模型

以結構化 match record 取代單一 `twReleased` boolean。每筆資料使用以下狀態：

- `confirmed`：台服公告名稱／內容已人工核對，且有可追溯台服公告；圖片可作為輔助證據。
- `probable`：名稱語意有合理對應，並有圖片素材或其他公告證據支持，但尚未達到官方名稱確認標準。
- `unmatched`：目前資料中找不到足夠對應證據；不可直接寫成「台服不會發行」。

判斷順序：

1. 先以韓文正式品名、台服中文正式品名與人工維護的語意／別名對照找候選。
2. 再用圖片 UUID、圖片內容或公告內文驗證候選；圖片證據不能單獨升級為 `confirmed`。
3. 多個候選或只有弱圖片命中時保留 `probable`，不自動覆蓋人工判斷。
4. 每個 confirmed／probable match 都保存 `krId`、`twThreadId`、台服名稱、台服日期、方法與備註，讓前端能展示證據來源。

現有人工提醒與 `VERIFIED_TW_MAP` 必須遷移為可讀的資料記錄，不得丟失；未經核對的 UUID 命中只能作為候選證據。

### 5. 分類與資料完整性

分類規則固定如下：

- `전설 패션 장비`、`에픽 패션` → `傳說時裝`。
- `토탈 패키지` → `套組時裝`，包含 `그랜드 앙상블 토탈 패키지`。
- `패션 럭키박스`、`펫 럭키박스` → `幸運箱`，依公告正文拆成個別產品。
- 通行證、聯動、其他商城維持既有分類。
- 樂器選擇箱保留每個選擇箱為一筆產品，並記錄組成品項。
- 染色劑選擇箱依公告正文的每個正式選擇箱拆分，記錄顏色／組成品項與銷售期間。

資料刷新流程要先確認韓服 VPN 可用，再依序更新清單、候選、詳細正文、台服清單／正文，最後建置 dataset 與圖片。抓取失敗時保留舊資料並在輸出中明確回報，不以空結果覆蓋既有資料。

### 6. 搜尋、篩選與響應式行為

- 搜尋同時比對韓服名稱、台服名稱、公告標題、分類與公告 ID。
- 分類可多選；台服狀態提供全部／官方確認／可能對應／尚未找到對應。
- 控制列在桌面吸頂；手機以橫向滾動分類列搭配篩選面板，避免佔滿首屏。
- 桌面卡片使用 3–4 欄；手機使用單欄，圖片與文字都保持可讀，不以放大圖片填滿寬度。
- 輪播箭頭在桌面 hover 時顯示，手機常駐可觸控區；提供鍵盤左右鍵、`aria-label` 與 `prefers-reduced-motion` 支援。
- 狀態不可只用顏色區分；所有 badge 都必須有完整文字。
- 無結果時顯示目前搜尋／篩選條件與一鍵清除。

## 實作邊界

### 會修改

- `index.html`：概覽、控制列、狀態說明與可存取標籤。
- `css/style.css`：編輯式時間軸、控制列、卡片、響應式與輪播互動樣式。
- `js/app.js`：排序、時間錨點、篩選、雙語搜尋、狀態呈現與觸控輪播。
- `scripts/build-dataset.js` 與相關解析腳本：分類、選擇箱拆分、match record 生成。
- `data/raw/` 中必要的可追溯對照資料，以及 `data/fashion.json` 和圖片資產。
- `README.md`：重新抓取流程、判斷證據與分類說明。

### 不會做

- 不引入後端、資料庫或前端框架。
- 不把韓服日期當成台服發行預測模型。
- 不以未核對的圖片相似或 UUID 命中宣稱官方已發行。
- 不改變圖片版權或官方來源聲明。

## 驗收條件

1. 首次載入時按韓服日期正序顯示，且可切換倒序與跳到今天。
2. `傳說時裝` 與 `套組時裝` 分類完全符合韓服標題規則；`그랜드 앙상블 토탈 패키지` 出現在套組時裝。
3. 樂器與染色劑選擇箱的每個正式產品都有資料、來源與可瀏覽圖片。
4. 台服狀態可分辨 confirmed、probable、unmatched，且前端可查看證據來源。
5. 雙語名稱、分類、公告 ID 都能搜尋；手機能完成篩選、排序與圖片切換。
6. 沒有因抓取失敗而清空既有資料；腳本能報告 VPN／HTTP／解析錯誤。
7. `node --check`、資料一致性檢查、資料建置 dry-run 通過；桌面與手機 viewport 都完成瀏覽器 smoke test。
